# Оновлення прошивки з GitHub

Три програмні етапи реалізовані: пакет релізу, OTA на ESP32-C6 та кнопки
у вебпанелі. Версія — **0.2.1**. Підтримується профіль `esp32c6_rgb8`,
Zigbee + Wi-Fi, підтверджені 4 MiB flash. Matter і generic-профілі не отримують OTA.

## Одноразовий перехід через USB

Стара прошивка має лише `factory`. Потрібно один раз записати новий bootloader,
таблицю розділів, початковий `otadata` та застосунок через USB.
Звичайний OTA application не змінює таблицю розділів.

| Розділ | Адреса | Розмір |
| --- | --- | --- |
| nvs | `0x9000` | `0x6000` |
| phy_init | `0xf000` | `0x1000` |
| ota_0 | `0x10000` | `0x1e0000` (1,875 MiB) |
| otadata | `0x1f0000` | `0x2000` |
| zb_storage | `0x210000` | `0x10000` |
| ota_1 | `0x220000` | `0x1e0000` (1,875 MiB) |

Адреси й розміри NVS та Zigbee-сховища збережені. `erase-flash` не потрібен.
Стандартна команда flash записує чотири артефакти; NVS і Zigbee-сховище
не включені до списку запису. Збереження даних на пристрої ще потрібно перевірити.
Експорт для VS Code також копіює `ota_data_initial.bin` у папку IDE-збірки.
Якщо після переходу на OTA кнопка Flash повідомляє про відсутність цього файла,
виконайте Build, щоб оновити експортовані артефакти.

Для наявної папки збірки перевірте в `build/esp32c6_rgb8/sdkconfig`:

```ini
CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y
CONFIG_PARTITION_TABLE_CUSTOM=y
CONFIG_PARTITION_TABLE_CUSTOM_FILENAME="boards/esp32c6_rgb8/partitions.csv"
CONFIG_ESPTOOLPY_FLASHSIZE_4MB=y
```

Defaults не замінюють наявний sdkconfig. CMake відхиляє основний профіль без
rollback або з іншою назвою таблиці. Для нової папки defaults уже правильні.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/idf.ps1 -Action build
# Лише за свідомого запуску користувачем; замініть COM5 своїм портом.
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/idf.ps1 -Action flash -Port COM5
```

## Пакет і публікація релізу

```powershell
python scripts/package_firmware.py --output build/firmware-0.2.1
```

Вихідна папка має бути новою. Скрипт створює application `.bin`, `manifest.json`
та `SHA256SUMS`. Звіряє версію всередині образу з метаданими, чип, профіль,
варіант, rollback, місткість слота та фактично зібрану таблицю розділів.
Bootloader, дамп NVS і sdkconfig до OTA-пакета не входять.

Контракт manifest v1: `repository`, `project`, `board`, `target`, `variant`,
`version`, `file`, `size`, `sha256`, `ota_ready: true`, `layout: c6-4m-ota-v1`.
`size` — байти, SHA-256 — 64 малі hex-символи. Ім’я binary має бути
`bt-home-esp32c6_rgb8-<version>.bin`. Версії — стабільні `X.Y.Z`, без початкових
нулів чи суфіксів; до шести цифр на компонент.

Для наступної версії змініть `PROJECT_VER` у `CMakeLists.txt`, збережіть потрібні
зміни в Git і завантажте їх у репозиторій. Workflow **Firmware release candidate**:

- вручну збирає пакет як artifact;
- на push тега `vX.Y.Z` запускає тести й збірку, звіряє тег із версією образу;
- створює **чернетку GitHub Release** із трьома файлами пакета.

Після перевірки обладнання опублікуйте чернетку як стабільний реліз
у `Yaroslav1205/B-T-HOME`. Пристрій читає публічний
`https://github.com/Yaroslav1205/B-T-HOME/releases/latest/download/manifest.json`,
а binary — `/releases/download/v<version>/<file>`. Приватні репозиторії,
чернетки й prerelease не підтримуються. Токен GitHub у прошивку не записується.
Workflow використовує стандартний `GITHUB_TOKEN` з `contents: write`.
Не замінюйте файли опублікованої версії; випускайте новий тег.
SHA-256 перевіряє цілісність, HTTPS — сервер. Це не цифровий підпис прошивки;
джерелу та правам публікації в репозиторії потрібно довіряти.

## Вебпанель та API

Перемкніть BOOT у Wi-Fi-клієнт, підключіть пристрій до роутера з інтернетом
і відкрийте його локальну IP-адресу. Увійдіть і відкрийте **Оновлення прошивки**:

1. **Перевірити оновлення** — прочитати останній manifest.
2. **Оновити прошивку** — підтвердити встановлення й перезапуск.
3. Дочекатися завантаження, перевірки та перезапуску; увійти повторно.

Оновлення дозволене лише для строго новішої версії. Повторні запити під час
роботи відхиляються. До синхронізації часу панель пропонує повторити спробу.
SNTP працює у Wi-Fi-клієнті навіть при групі відключень 0. AP і Zigbee не мають
інтернет-завантаження. Віддалений доступ до самої панелі через інтернет не додається.

`GET /api/ota`: `supported`, `connected`, `busy`, `current_version`, `version`,
`state`, `error`, `received`, `total`. Стани: `idle`, `checking`, `available`,
`up_to_date`, `downloading`, `restarting`, `error`.

`POST /api/ota`: `{"action":"check"}` або `{"action":"install"}`; потрібні
чинний сеанс і `X-BTH-Request: 1`. Відповідь 202, неправильна дія — 400,
відсутній сеанс — 401, немає захисного заголовка — 403, зайнятість,
непідтримувана таблиця або відсутність Wi-Fi-клієнта — 409.
Довга операція виконується після прийняття запиту, результат читається через GET.

## Виконання та відкат

`OtaService` ін’єктується з composition root до `RelayWeb`, який керує його
init/start/stop/deinit. Кількість слотів Runtime залишається 16. HTTP надсилає
команди через чергу на один елемент, читає копію статусу через окрему чергу.
Worker володіє TLS, SHA-256 і OTA-дескриптором. Мережі та запису flash у tick немає.
Stop завершує HTTP, сигналізує worker і чекає його завершення перед звільненням
черг та Wi-Fi. BOOT і зміна мережевих налаштувань під час OTA заблоковані.

HTTPS перевіряє сертифікат через bundle ESP-IDF. Перенаправлення дозволені лише
на шлях релізів заданого репозиторію та HTTPS-хости GitHub release assets,
до п’яти HTTP-відкриттів. Таймаут мережевого виклику — 5 с; бюджет операції —
180 с, перевіряється між викликами. Stop може чекати поточний мережевий виклик
або ланцюжок перенаправлень.

До стирання перевіряються чип, назва проєкту та версія образу. Запис іде лише
в неактивний слот. Перевіряються точна довжина, SHA-256 і валідація ESP-IDF.
Лише після цього змінюється boot partition. Помилки залишають поточну прошивку
активною; повтор — за новим запитом користувача.

Через приблизно 2 с після успіху головна задача зупиняє Runtime і перезапускає
пристрій. Новий образ підтверджується після 30 с успішної роботи циклу й модулів.
Це перевірка життєвого циклу, а не фізичної справності всіх сенсорів.
Скидання/втрата живлення до підтвердження запускає відкат bootloader.
Якщо фатальна помилка зупинила застосунок без reset, відкат відбудеться після
наступного перезапуску. Автоматичних reboot-циклів немає.

## Перевірки й межі

Успішні: 10 наборів host-тестів, 4 тести пакування, браузерна перевірка Edge
та збірки основного ESP32-C6 і чотирьох generic-профілів (ESP32-C6, C3, S3,
ESP32) на ESP-IDF v5.4. Тести OTA охоплюють фрагментовані
читання, обрізаний/зайвий вміст, неправильний чип/проєкт/версію, помилки запису,
SHA, завершення й активації, скасування. Пакет 0.2.0 сформований локально.
Для 0.2.1 повторно пройдено 10 наборів host-тестів, 4 тести пакування та
збірку основного профілю ESP32-C6 на ESP-IDF v5.4.
GitHub workflow та завантаження з реального релізу на ESP32 не перевірялися;
плату не прошито. Публікація пакета не означає перевірку на обладнанні.

Перед публікацією перевірити на пристрої: USB-перехід і збереження NVS,
оновлення на наступну версію, обидва слоти, втрату Wi-Fi/живлення під час запису,
відкат до підтвердження, несумісний/пошкоджений образ і продовження вимірювань/реле.

Основи: [ESP-IDF v5.4 OTA](https://docs.espressif.com/projects/esp-idf/en/v5.4/esp32c6/api-reference/system/ota.html).
