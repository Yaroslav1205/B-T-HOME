# Огляд проєкту — 09.10.2026

Основа придатна для подальшого розвитку: невеликий Runtime, явне складання
застосунку, переносна логіка та окремі драйвери. Переписування архітектури
не потрібне. Виправлення цього огляду стосуються конкретних відмов і перевірок
вхідних даних, без додаткових задач, реєстрів сервісів чи бібліотек.

## Обсяг огляду

Переглянуто прикладний код компонентів, composition root, CMake/Kconfig,
профілі плат, скрипти native/Matter/IDE, шаблон нового модуля, тести та основні
контракти документації. Вихідний стан містив незакомічені зміни; вони збережені.
Сторонні SDK та бінарні радіобібліотеки не проходили повного аудиту.

| Ділянка | Що перевірено |
| --- | --- |
| `bth_core`, `main` | Порядок постачальників, час життя посилань, 16 слотів, відкат часткового запуску, припинення tick після відмови |
| `bth_relay`, `RelayService` | Commit перед GPIO, обмежені черги, поділ HTTP/асинхронних відповідей, зупинка worker, повторний запуск |
| `bth_radio`, BOOT, Zigbee | Взаємовиключність мережевих режимів, очищення груп, debounce, обмежене вікно сполучення, SDK lock і callbacks |
| AC/DC, історія, батарея | Межі накопичення, достовірність і свіжість, розриви вимірювань, контрольні точки, відмова NVS |
| OLED, RGB, heartbeat | Обмежені буфери, планування, відсутній OLED, завершення I²C worker до звільнення ресурсів |
| Доступ і web | Валідація налаштувань, сеанси, межі запитів, підтвердження реле, копії вимірювань між задачами |
| Matter | Вхідні команди через relay worker, синхронізація атрибутів, повтори сполучення, окрема конфігурація та збірка |
| Інструменти | Явні джерела CMake, відокремлені конфігурації плат, SUBST для пробілів у шляху, native/IDE кеші, host-тести й CI |

## Виправлено

1. **Застаріла готовність реле після stop.** Черга стану зберігала `ready=true`
   після завершення worker. `post()` міг прийняти команду, яку вже нікому виконати.
   Тепер stop публікує вимкнений стан із `ready=false`, зберігаючи `saved_on`.
   Готовність після start публікується лише після успішного створення задачі.
   Помилку відтворено регресійним тестом до виправлення.
2. **Повторна ініціалізація сервісу реле.** Захищено ресурси від перезапису
   дескрипторів повторним init; start до успішного init або під час роботи
   повертає `invalid_state`. Тести охоплюють кожну з чотирьох відмов виділення
   черг/семафора, невдале створення worker та повторний запуск.
3. **Некоректне тіло HTTP-команди.** Порівняння C-рядків приймало п'ять байтів
   `true` + NUL як команду ввімкнення. Тепер порівнюються всі отримані байти.
4. **Необмежена структурна складність JSON.** Ліміту 511 байтів недостатньо
   для обмеження глибини рекурсії cJSON. Перед парсером відхиляються вкладені
   об'єкти й масиви; API використовує лише пласкі об'єкти. Відхиляються також
   `\u0000`, які могли обрізати рядок налаштувань. Екрановані лапки, зворотні
   скісні риски та звичайний Unicode залишаються допустимими.
5. **Непридатний інтервал опитування.** Kconfig дозволяв до 1000 мс, хоча
   ADC читає обмежену кількість відліків, а BOOT відкидає прогалини понад 250 мс.
   Для плат з ADC, BOOT або RGB компілятор тепер вимагає не більше 50 мс.
   Поточні 20 мс і калібрування збережені.
6. **Зламана збірка ESP32-C3.** Вимога lock-free `atomic<bool>` стояла в ADC ISR,
   який реєструється лише на C6, але компілювався й для інших чипів. C3 не має
   тієї самої гарантії атомарності. Сам C6-обробник тепер компілюється тільки
   для C6; обмеження апаратної підтримки ADC не розширювалися.
7. **Завершення тестів при відмові.** Перевірка багатопотокового relay-тесту
   більше не запускає деструктори незавершених `std::thread` при аварійному
   виході. Для CTest задано таймаут 30 с, щоб регресія не зависала безстроково.

## Як зберігати проєкт простим

Змінювати логіку у відповідному `bth_<module>`, апаратні виклики — у
`bth_platform`, GPIO — у профілі плати. Новий модуль підключати явно лише через
`main/application.cpp`; порядок створення та реєстрації залишати видимим.
Власну задачу додавати тільки для реального блокувального I/O. Зразок розширення —
[ADDING_MODULE.md](ADDING_MODULE.md), правила життєвого циклу —
[ARCHITECTURE.md](ARCHITECTURE.md).

Найбільша додаткова складність зосереджена в необов'язковому Matter-адаптері:
кілька сумісних представлень напруги й окремий SDK. Це наявна функціональність;
її видалення змінить можливості пристрою. Основний профіль залишається Zigbee + AP.

## Межі впевненості

Host-тести підміняють апаратні інтерфейси, FreeRTOS і частину NVS. Браузерний
тест використовує підставний HTTP API. Вони не підтверджують реальні відмови
драйверів, механічне спрацювання реле, точність вимірювання чи сумісність шлюзу.
Завершення SDK-задач і callbacks під час багаторазового перемикання радіо
потребує перевірки на платі; очікування завершення worker покладається на SDK.

Плату в цьому огляді не прошивали. Перед апаратним прийманням перевірити
повторні переходи Zigbee ↔ AP, відновлення збереженого стану після втрати живлення,
помилки/відсутність OLED, відновлення вимірювань після затримок і залишок стека.
Результати компіляції та команд перевірки наведено в [BUILD.md](BUILD.md).
