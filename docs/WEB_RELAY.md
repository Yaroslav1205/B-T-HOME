# Вебкерування реле

«Оновлення прошивки» розташоване останньою панеллю. «Показники» одночасно
відображають напруги AC/DC, середню напругу мережі, приблизну автономність,
поточний і попередній періоди живлення, підтверджений стан реле, IP та
поточний/найближчий плановий інтервал відключення з групою і станом даних.
Середнє та автономність беруться з тієї самої моделі, що й OLED.

`GET /api/voltages` додатково повертає `display`: `age_ms`, `average_volts`,
`battery_minutes`, `mains_present`, `relay_on`, `ipv4`, `outage_state`,
`outage_group`, `outage_begin`, `outage_end`. Недоступні числові покази та
невідомий стан реле — `null`; недоступна IP-адреса — порожній рядок.
`battery_minutes` надається лише при відсутності мережі й достовірній оцінці;
на сторінці понад 5999 хв показується `>99:59`, як на OLED.
Стани графіка: `hidden`, `unavailable`, `stale`, `clear`, `interval`;
межі інтервалу — хвилини від початку доби. Без свіжої копії (2,5 с)
поле `display` відсутнє; браузер також прибирає прострочені покази.

Панель має розділ «Оновлення прошивки» з поточною версією, перевіркою GitHub,
підтвердженням встановлення, прогресом і помилками. Потрібні Wi-Fi-клієнт з
інтернетом та OTA-таблиця розділів. [API і початкове встановлення](OTA.md).

У **Matter-збірці** веб працює у домашній Wi-Fi мережі після сполучення через
Matter-контролер. IP друкується в USB-консолі (`Web: http://...`); вхід — збережені
облікові дані, спочатку `admin / admin`. Блок «Пристрій» показує MAC станції.
Wi-Fi налаштовує Matter-контролер, відповідні поля AP приховані; зміну мережевих
параметрів через HTTP API відхилено. BOOT відкриває сполучення на 5 хвилин.
Наведений нижче опис AP/STA/Zigbee стосується основної збірки без Matter.
[Matter: збірка та підключення](MATTER.md).

У профілі `esp32c6_rgb8` короткий **BOOT (GPIO9)** перемикає **AP → STA → Zigbee → AP**.
Вибір зберігається в NVS; без запису запускається AP. Веб працює в AP та STA:
відповідно `http://192.168.4.1` або IP від роутера (OLED/USB-консоль).
Реле й вимірювання залишаються активними. Сполучення Zigbee запускається
утриманням BOOT 3 с із відпусканням у Zigbee. Секція Zigbee у вебі прихована.

В окремому розділі «Підключення до роутера» після «Налаштувань доступу» задайте
SSID та паролі **основної й резервної мережі**. Кнопка «Зберегти мережі» не
змінює назву/пароль точки пристрою чи вебобліковий запис і не зберігає
незавершені зміни в іншому розділі.
Режим клієнта пробує їх по черзі, до 15 с на підключення разом із DHCP, доки
не отримає IP. Після втрати зв’язку пошук продовжується з наступного слота.
Порожній SSID видаляє слот. Без обох мереж клієнт чекає перемикання BOOT.
Порожній пароль зберігає попередній лише для незміненого SSID; для відкритої
мережі є явний прапорець. Нові параметри застосовуються при наступному вході
в режим клієнта або після перезапуску; поточне з’єднання не переривається.
LED: 1 — AP, 2 — режим STA незалежно від IP, 3 — Zigbee, 8 — сполучення Zigbee.

Точка використовує WPA2-PSK/AES (CCMP), необов'язковий PMF та явну адресу
`192.168.4.1/24`. DHCP готується до події запуску AP після встановлення адреси.
Для діагностики зависання телефона на отриманні IP термінал показує:
`AP ready ... DHCP started` → `Client joined ... waiting for DHCP` →
`DHCP assigned ...`. Відключення містить числовий `reason` від Wi-Fi драйвера.
Діагностичні callbacks реєструються після стандартних обробників SDK та
видаляються перед звільненням мережевого інтерфейсу. Паролі не друкуються.
Ці повідомлення дозволяють розрізнити готовність DHCP, приєднання телефона
та видачу адреси; усунення проблеми на конкретному телефоні потребує фізичної перевірки.

`GET /api/settings` додатково повертає `primary_ssid`, `backup_ssid`,
`primary_open`, `backup_open`, без паролів. `PUT /api/settings` приймає ці поля
та `primary_password`, `backup_password`. Поля доступу `ssid`, `wifi_password`,
`username`, `web_password` можна не передавати при збереженні мереж роутера —
тоді вони залишаються незмінними; якщо передане хоча б одне, потрібні всі чотири.
Для кожного слота всі три поля
передаються разом; відсутня трійка зберігає старий слот. SSID — до 32 байтів
UTF-8, пароль захищеної мережі — 8–63 друкованих ASCII-символи. Ліміт JSON —
2047 байтів. Потрібні чинний сеанс і `X-BTH-Request: 1`.
AccessConfig v2 (`bth_access/config_v2`) переносить AP і вебобліковий запис із
`config_v1`, додаючи два порожні слоти. Пошкоджені записи не скидаються.

API адаптера (для конфігурацій із доступним `ZigbeeControl`): секція **Zigbee** показує стан приєднання та дозволяє сполучити реле зі шлюзом
або скинути його Zigbee-прив’язку. `GET /api/zigbee` повертає `state`, `channel`,
`seconds_left`; `POST /api/zigbee` приймає `{ "action": "join" }` або
`{ "action": "reset" }`. Потрібні вхід і `X-BTH-Request: 1` для зміни.
`202 Accepted` означає прийняття в чергу, фактичний результат надходить через GET.
У збірці без Zigbee стан — `disabled`, елемент керування прихований, POST повертає 409.
[Інструкція сполучення](ZIGBEE.md).

Поруч із напругами показуються поточний та попередній періоди основного
живлення, із підписом наявності/відсутності та тривалістю у хвилинах або годинах.
`GET /api/voltages` також повертає `current_period` і `previous_period`:
об'єкти `{ "present": true, "duration_ms": 120000 }`, або `null`, якщо стан
невідомий чи вимірювання мережі недостовірне/застаріле. Тривалість відповідає
останньому вимірюванню, оновлюється щосекунди та не залежить від відкриття вебсторінки.
[Поріг, відлік і скидання історії](MAINS.md#облік-часу-живлення).

Поточний профіль `esp32c6_rgb8` використовує **GPIO19, активний HIGH** для реле
та GPIO8 для RGB-індикації. Підключення й полярність реле підтверджені користувачем.
Перший запуск без збереженого стану залишає реле вимкненим.

## Підключення та початкові дані

1. Зберіть прошивку: `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/idf.ps1`.
2. Короткими натисканнями BOOT виберіть AP (1 спалах). Підключіться до **B-T HOME XXXX** з паролем **12345678**.
   `XXXX` — останні два байти MAC саме Wi-Fi AP, записані чотирма великими hex-символами,
   включно з початковими нулями. Наприклад, MAC `xx:xx:xx:xx:1B:A4` → `B-T HOME 1BA4`.
3. Відкрийте **http://192.168.4.1**, введіть логін **admin** і пароль **admin**.
4. У розділі **Налаштування доступу** змініть назву Wi-Fi, пароль Wi-Fi, логін
   або пароль сторінки. Порожнє поле нового пароля залишає поточний пароль.

Wi-Fi використовує WPA2. Інтернет і captive portal не потрібні. HTML містить
форму входу; читання стану, керування реле та налаштування потребують чинного сеансу.
Публічні початкові дані доступу задані на прохання користувача. Нові паролі не
виводяться в журнал та не повертаються з API.

## Оформлення сторінки

Після входу блок **Пристрій** показує MAC-адресу Wi-Fi точки доступу у форматі
`AA:BB:CC:DD:EE:FF`. Це адреса AP, з останніх двох байтів якої формується
початкова назва `B-T HOME XXXX`, а не адреса Zigbee. Поле `mac` надходить
у відповіді `/api/relay` з адреси `ESP_MAC_WIFI_SOFTAP` реального пристрою.

Кнопка **Темна тема / Світла тема** доступна до й після входу. Вибір зберігається
локально в цьому браузері й відновлюється при повторному відкритті сторінки.
До першого ручного вибору сторінка використовує системну тему пристрою.
Це налаштування браузера, воно не записується у flash ESP32.

## Зміна доступу

- SSID: 1–32 байти UTF-8; Wi-Fi пароль: 8–63 друковані ASCII-символи.
- Логін сторінки: 1–32 друковані ASCII-символи; пароль: 1–63 байти UTF-8.
  Новий пароль сторінки потрібно повторити у формі. Паролі з керівними символами
  відхиляються сервером.
- Спочатку весь набір налаштувань зберігається одним версійованим blob у NVS
  (`bth_access/config_v2`) із commit. Успішна відповідь надходить після збереження.
- Через секунду після відповіді зміни Wi-Fi застосовуються без перезапуску ESP32.
  Телефон/комп'ютер потрібно перепідключити до нової мережі з новим паролем.
  Реле продовжує працювати; Wi-Fi зміни не змінюють його стан.
- Якщо поставити застосування Wi-Fi в чергу не вдалося, сторінка повідомляє про
  необхідність перезапуску. Якщо сам драйвер відхилив застосування, адаптер
  намагається відновити попередню мережу; нові дані залишаються збереженими.
- Зміна логіна чи пароля сторінки завершує всі сеанси. Наступний вхід — із новими
  даними. Кнопка **Вийти** завершує поточний сеанс.
- Пароль сторінки зберігається як PBKDF2-HMAC-SHA256 (10 000 ітерацій, випадкова сіль
  16 байтів), а пароль Wi-Fi — у вигляді, потрібному драйверу. Шифрування NVS/flash
  і HTTPS у цьому проєкті не налаштовані; вебдоступ працює через локальний HTTP.
- До 4 сеансів із випадковими 128-бітними токенами; cookie `HttpOnly`, `SameSite=Strict`,
  тривалість 1 година. Після перезапуску потрібен повторний вхід. Після п'яти невдалих
  входів у 30-секундному вікні наступні спроби блокуються до кінця цього вікна.

Після оновлення попередньої версії з випадковим AP-паролем нові defaults
застосуються один раз, якщо `bth_access/config_v1` і `config_v2` ще відсутні. Старий ключ
`bth_wifi/ap_password` більше не використовується; NVS не стирається, стан реле
зберігається. Уже змінені через новий вебінтерфейс дані наступні збірки не
перезаписують. Автоматичного скидання забутих паролів немає.

## Поведінка

- Кнопка задає явний стан ON/OFF. Повторення тієї самої команди не перемикає реле
  вдруге й не створює зайвого запису flash.
- Новий стан підтверджується лише після успішного `nvs_commit` та встановлення GPIO.
  Зворотний зв'язок означає **підтвердження прошивкою**, не вимірювання контактів реле.
- Сторінка отримує стан раз на 1,5 секунди; поки виконується команда, кнопка заблокована.
  При втраті зв'язку стан стає невідомим; відновлення зв'язку зчитує стан з пристрою.
- Після вимкнення/ввімкнення живлення останній підтверджений стан відновлюється
  до запуску вебсервера. Якщо живлення зникло під час команди до відповіді,
  після запуску потрібно повторно прочитати стан: запис міг уже завершитися.
- Запис виконується перед встановленням GPIO. Якщо запис завершився, але керування
  GPIO повернуло помилку, збережений бажаний стан залишається в NVS, а стан виходу
  позначається невідомим. Сторінка не повідомляє про успіх.
- Помилка запису не змінює вихід; достовірність збереження позначається втраченою,
  наступні команди блокуються до перезапуску. NVS ніколи не стирається автоматично.
- Зупинка застосунку вимикає вихід, але не змінює збережений стан для наступного запуску.
  До запуску прошивки рівень входу реле визначається апаратною схемою плати.

## Організація коду

| Частина | Файли |
| --- | --- |
| Валідація, defaults та збереження доступу | `components/bth_access/`, `components/bth_platform/src/access_store.cpp` |
| Логіка стану й порядок збереження | `components/bth_relay/` |
| GPIO, NVS, черги та worker | `components/bth_platform/src/esp_relay.cpp`, `nvs_storage.cpp`, `relay_service.cpp` |
| Власна Wi-Fi мережа | `components/bth_platform/src/wifi_ap.cpp` |
| HTTP API | `components/bth_web/src/relay_web.cpp` |
| Сторінка українською, без зовнішніх залежностей | `components/bth_web/web/index.html` |
| Підключення модулів | `main/application.cpp` |
| GPIO та полярність | `boards/esp32c6_rgb8/board.json` |

`RelayController` не залежить від SDK. Після запуску тільки worker реле виконує
команди та запис NVS; Runtime.tick не чекає flash. HTTP-обробник передає команди
через чергу на 4 елементи й чекає відповідь до 3 секунд. Запізнілі відповіді
відрізняються ID; знімок стану передається окремою чергою довжини 1.
При зупинці спочатку завершується HTTP-задача, потім worker реле, а NVS закривається
після всіх споживачів. Помилка виконання вебкоманди повертається через API;
це не помилка lifecycle і не запускає загальний відкат Runtime.

Функцію можна вимкнути в menuconfig → `B-T HOME application` →
`Enable Wi-Fi AP and relay web control`. Generic-профілі без `relay_gpio` не
налаштовують випадковий GPIO; сторінка показує недоступність реле.

## API

- `GET /` — HTML із формою входу.
- `POST /api/login` — JSON `username`, `password`; встановлює cookie сеансу.
- `POST /api/logout` — завершує сеанс.
- `GET /api/settings` — поточні `ssid`, `username`, `wifi_pending`; без паролів.
- `PUT /api/settings` — JSON `ssid`, `wifi_password`, `username`, `web_password`.
  Порожній новий пароль означає залишити попередній. Відповідь містить `reconnect`,
  `login_required`, `restart_required`, `ssid`.
- `GET /api/relay` — `ready`, `on`, `saved_on`, `output_known`, `storage_known`, `error`.
- `PUT /api/relay`, заголовок `X-BTH-Request: 1`, тіло JSON `true` або `false` —
  встановити стан. HTTP 200 означає підтвердження, 503 — відмову/непідтверджену
  команду; після таймауту прочитайте `GET`. Значення `on` достовірне лише коли
  `output_known=true`, `saved_on` — коли `storage_known=true`.

Усі POST/PUT потребують `X-BTH-Request: 1`; реле й налаштування потребують cookie.
Без чинного входу API повертає 401, неправильні дані — 400, обмеження входів — 429.
JSON-запити — пласкі об'єкти обсягом до 511 байтів: вкладені об'єкти, масиви,
нульові байти та `\u0000` відхиляються до запуску парсера. Це обмежує рекурсію
на стеку HTTP-задачі й запобігає обрізанню облікових даних. Тіло команди реле
має точно дорівнювати `true` або `false`, без додаткових байтів.
Зміна стану через GET заборонена. CORS не ввімкнений, PUT потребує власного
заголовка; стороння вебсторінка не може керувати реле звичайною HTML-формою.

## Напруга мережі та батареї

Після входу над керуванням реле показуються дві напруги: **Мережа** (AC RMS)
та **Батарея** (DC-вхід GPIO0). Формат — `230.5 V` / `12.4 V`, один десятковий
знак. Сторінка опитує покази разом зі станом реле приблизно кожні 1,5 секунди;
самі вимірювання оновлюються раз на секунду. Калібрування й дільники ті самі,
що для OLED, окремих вимірювань HTTP-обробник не запускає.

`GET /api/voltages` потребує cookie чинного сеансу. Приклад відповіді:

```json
{"mains":{"status":"ok","volts":230.5,"age_ms":120},"battery":{"status":"ok","volts":12.4,"age_ms":120}}
```

Стани: `waiting` — ще немає даних, `uncalibrated` — мережа потребує калібрування,
`invalid` — недійсний результат, `stale` — немає нового звіту 2,5 секунди,
`ok` — свіжий достовірний показ. Для будь-якого стану, крім `ok`, `volts` дорівнює
`null`, а UI показує риску та пояснення. Вік даних до першого звіту — `null`.
Браузер також прибирає прострочене число, навіть поки новий запит очікує відповіді.
Недоступність показів не блокує керування реле; вихід із сеансу очищає покази.

`RelayWeb` реалізує `MainsSink` та `DcSink`; composition root передає звіти
паралельно в OLED, лог і web. Задача Runtime публікує копію обох показів у
FreeRTOS-чергу на один елемент, HTTP-задача читає знімок без очікування.
Черга створюється в `init` і видаляється після завершення HTTP-задачі в `deinit`.
Жодного спільного незахищеного читання `double` між задачами немає.

Host-тести перевіряють свіжість, калібрування, нульову напругу та некоректні числа.
Browser-тест із mock API перевіряє обидва покази, оновлення, помилки, локальне
прострочення й очищення при втраті зв'язку та виході. Перевірка фізичних показів
потребує прошивання й звірки з вимірювальним приладом.

## Помилка 431: завеликі HTTP-заголовки

Ліміт заголовків запиту — 4096 байтів (`CONFIG_HTTPD_MAX_REQ_HDR_LEN` у
`sdkconfig.defaults`). Стандартні 512 байтів ESP-IDF можуть бути замалими для
запитів браузера з User-Agent, Cookie та іншими заголовками. Перевищення ліміту
дає `431 Request Header Fields Too Large` до виклику обробника сторінки/API.

Для вже створеної збірки встановіть 4096 у menuconfig → Component config →
HTTP Server → Max HTTP Request Header Length: defaults не перевизначають
наявний `build/<profile>/sdkconfig`. Перезберіть і прошийте пристрій.
Якщо запит перевищує й 4096 байтів, перевірте його заголовки в інструментах
розробника браузера та видаліть зайві cookie для адреси пристрою.

## Звуковий сигнал відсутності мережі

Після входу розділ **Звуковий сигнал** дозволяє зберегти інтервал у секундах:
ціле число **0–86400**, типово **20**. **0** вимикає також перший сигнал.
За ненульового значення сигнал 200 мс подається одразу після підтвердженого
зникнення мережі, далі повторюється з указаним інтервалом. Зміна застосовується
без перезапуску та зберігається після вимкнення живлення. GPIO21 активний HIGH.
Без налаштованого бузера цей розділ приховується.

- `GET /api/buzzer` → `{"available":true,"interval_seconds":20}`;
  без бузера → `{"available":false}`.
- `PUT /api/buzzer`, тіло `{"interval_seconds":0}`, заголовок `X-BTH-Request: 1`:
  після успішного commit повертає поточне значення у форматі GET.
- Обидва запити потребують сеансу. Дробові, від’ємні, завеликі, рядкові або
  відсутні значення повертають `400 invalid_interval`; без бузера PUT повертає
  `404 buzzer_unavailable`; помилка збереження — `503 save_failed`.

Налаштування зберігається окремо в `bth_buzzer/interval_s`, без зміни схеми
облікових даних. Після помилки NVS чинне значення зберігається в оперативній
пам’яті; повторний запис потребує перезапуску. Після втрати HTTP-відповіді слід
оновити сторінку та прочитати фактично збережене значення.

## Струм споживання у вебпанелі

Після входу відкрийте «Розрахунок автономності» та задайте цілий струм
від 1 до 100000 мА (1000 мА = 1 А). Типове значення — 58 мА.
Кнопка «Зберегти струм» зберігає значення в NVS (`bth_battery/discharge_ma`)
і застосовує його без перезапуску. Поточний заряд зберігається, минулі
витрати не перераховуються. Прогноз на OLED і подальший облік розряду
використовують нове значення. Це заданий струм, а не вимірювання.

Автентифіковані `GET /api/battery` і `PUT /api/battery` використовують
`discharge_ma` (ціле число мА); PUT має той самий захист, що інші зміни у вебі.
Нульові, дробові та позамежні значення відхиляються. HTTP публікує значення
через чергу довжиною 1 лише після успішного запису; власник Runtime читає
його після tick. Помилка збереження залишає попереднє активне значення.
# Графік відключень

Панель «Графік відключень» зберігає групу Чернівціобленерго **0–12**;
типово **2**, **0** вимикає запити та показ на OLED.
`GET /api/outages` повертає `{"available":true,"group":2}`;
`PUT /api/outages` приймає `{"group":0}` і повертає збережене значення.
Обидва запити потребують сеансу; PUT використовує ті самі перевірки
походження/заголовків, що інші зміни налаштувань. Дробові, відсутні та
позадіапазонні значення повертають 400 `invalid_group`; помилка запису —
503 `save_failed`. У Matter `available:false`, PUT повертає 404.
[Джерело графіка та поведінка](OUTAGES.md).


## Режими реле

Вебпанель має вибір: `0` — не використовується (вихід OFF), `1` — керування
з браузера, `2` — увімкнення при відсутності мережі. Вибір набирає чинності
без перезапуску. За відсутності ключа режиму збережено попередню поведінку — `1`.
У режимі `1` також зберігається наявне керування Zigbee/Matter; режими `0` і `2`
відхиляють їхні ручні команди. Вони не можуть перебити автоматику.

Автоматика отримує той самий підтверджений стан `MainsReading.history`, що й
бузер: достовірний калібрований вимір, відома відсутність мережі (нижче 100 В).
Повернення мережі, недійсний вимір або відсутність нового звіту 2,5 с вимикають
вихід. Після запуску режим `2` тримає OFF до першого достовірного звіту.
Задача реле перевіряє автоматичний вихід кожні 100 мс та після команд.
Це локальна логіка, незалежна від Wi-Fi та графіків відключень з інтернету.

`GET /api/relay` містить числове поле `mode`. `PUT /api/relay-mode` приймає
`{"mode":0}`, `{"mode":1}` або `{"mode":2}`; потрібні чинний сеанс і заголовок
`X-BTH-Request: 1`. Недійсне значення дає 400, відмова збереження — 503.
Ручний `PUT /api/relay` поза режимом `1` дає 409.

Режим записується окремим ключем `mode` у NVS `bth_relay` через наявну задачу
реле. Автоматичні переходи не пишуть NVS й не змінюють збережену ручну команду.
Повернення до режиму `1` відновлює останню збережену ручну команду.
Нових задач або слотів Runtime не додається. Host-тести перевіряють переходи,
блокування ручних команд, застарілі виміри, перезапуск та помилки запису.
