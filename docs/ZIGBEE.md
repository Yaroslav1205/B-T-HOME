# Реле B-T HOME через Zigbee

Профіль `esp32c6_rgb8` підтримує стандартний керований Zigbee On/Off-пристрій.
Використовується радіо ESP32-C6, зовнішнього модуля не потрібно. Це Zigbee End
Device з постійно ввімкненим приймачем, а не координатор або маршрутизатор.
Вимірювання та OLED продовжують працювати. Одночасна робота Wi-Fi AP і Zigbee
на одному ESP32-C6 має відоме обмеження: мережа AP може бути видимою, але
підключення клієнтів не працює. Увімкнення `CONFIG_ESP_COEX_SW_COEXIST_ENABLE`
цього не усуває. Espressif підтверджує обмеження й для Zigbee SDK 2.x:
[обговорення SoftAP + Zigbee](https://github.com/espressif/esp-zigbee-sdk/issues/273).
Тому прошивка перемикає режими кнопкою BOOT на підтвердженому GPIO9
(натискання замикає вхід на GND, активний LOW).

## Кнопка BOOT і режим налаштування

- Після ввімкнення живлення активний **Zigbee**, Wi-Fi AP вимкнено.
- Після завантаження **утримайте BOOT 3 с і відпустіть**: Zigbee повністю
  зупиняється, запускається Wi-Fi AP зі збереженими назвою та паролем.
  Вебінтерфейс доступний за `http://192.168.4.1`.
- Повторне утримання 3 с із відпусканням закриває веб, зупиняє Wi-Fi й
  повертає Zigbee зі збереженою прив’язкою. Веб-сеанс потрібно відкрити заново
  під час наступного входу в налаштування.
- Коротке натискання (від 50 мс до 3 с) у режимі Zigbee запускає пошук мережі
  на 2 хв. У режимі Wi-Fi коротке натискання нічого не змінює.

Перемикання не перезавантажує ESP32, не зупиняє relay worker і не стирає NVS.
Модулі ADC, OLED та історії живлення залишаються зареєстрованими й активними.
Режим не записується у flash: після перезапуску знову активний Zigbee.
На час Wi-Fi керування зі шлюзу Zigbee недоступне; у режимі Zigbee немає вебу.
Стан режиму друкується в USB-термінал.
LED показує стан серіями: **1 спалах — Wi-Fi**, **2 — Zigbee**,
**3 — пошук мережі для сполучення**. Спалах і проміжок — по 200 мс,
пауза між серіями — 2 с. Початкове швидке блимання триває 2 с.

Час завершення перемикання залежить від
зупинки мережевих задач; кнопка не викликає повторних перемикань під час утримання.

Не тримайте BOOT під час подачі живлення або натискання RESET — це штатна
кнопка завантажувача. Прошивка ігнорує кнопку, затиснуту на початку опитування,
до відпускання. Брязкіт фільтрується протягом 40 мс.

## Підключення до MOES TPP05-Z(US)

1. Прошийте повну збірку для `esp32c6_rgb8`, включно з таблицею розділів.
   Команда `scripts/idf.ps1 flash -Port COMx` прошиває потрібні образи.
   Не використовуйте лише `app-flash` при першому переході на цю версію.
2. У панелі MOES / її застосунку відкрийте шлюз і ввімкніть додавання
   Zigbee-пристрою. Розташуйте B-T HOME поруч під час першого сполучення.
3. У режимі Zigbee коротко натисніть BOOT. Якщо зараз увімкнено Wi-Fi,
   спочатку утримайте BOOT 3 с і відпустіть для повернення до Zigbee.
4. У USB-терміналі перевірте повідомлення `Join successful`.
   Пошук припиниться через 120 с; якщо шлюз не знайдено, натисніть коротко знову.
5. Перевірте увімкнення/вимкнення реле з панелі.

На першому запуску без збереженої мережі пошук автоматично відкривається на 2 хв.
Після успішного приєднання мережа зберігається; звичайний перезапуск її не стирає.
Якщо шлюз тимчасово недоступний, пристрій намагається відновити підключення.

### Діагностика невдалого сполучення

Увімкніть додавання саме Zigbee-пристрою на шлюзі MOES, а потім коротко натисніть
BOOT. Три спалахи LED означають відкрите вікно пошуку. Журнал показує:

- `Startup: status=..., factory_new=..., joined=...` — результат запуску і стан прив’язки.
- `Steering requested: channels=11-26, result=0` — SDK прийняв запит пошуку.
- `Join unsuccessful: status=3 (no_network)` — SDK не знайшов придатної мережі;
  перевірте режим додавання на шлюзі та відстань до нього.
- `trust_center_key_exchange_failed` — збій обміну ключами з центром довіри.
- `Join successful` — мережеве приєднання завершене; відсутність пристрою в
  інтерфейсі MOES після цього потребує перевірки розпізнавання моделі шлюзом.

Рядок `Join unsuccessful` без коду зі старої прошивки не визначає причину.
Для діагностики потрібен повний журнал `zigbee:` від запуску до результату
пошуку. Не стирайте flash для повторної спроби.

У поточному профілі секція Zigbee у вебі прихована, оскільки SDK у цьому
режимі зупинений. Перемикання BOOT не виконує скидання Zigbee-мережі.
Щоб відв’язати пристрій, використовуйте видалення на шлюзі, поки активний Zigbee.

Стан «Підключено» означає приєднання до Zigbee-мережі, а не підтвердження того,
що MOES створив елемент керування на екрані. **Фізична сумісність із TPP05-Z(US)
ще не перевірена.** Якщо панель не розпізнає пристрій, потрібна окрема інтеграція
Tuya. На прохання користувача Model Identifier змінено з `BTH-RELAY1` на
`TS0001` — позначення одноканального вимикача в сімействі Tuya `TS000x`.
Це експеримент із розпізнаванням моделі, а не повна емуляція Tuya-пристрою:
Manufacturer Name залишається `B-T HOME`, власний Tuya PID не налаштовано,
тип HA On/Off Output та набір кластерів не змінено. Зміна назви сама по собі
не гарантує усунення `no_network` чи появу елемента керування в MOES.
Джерело формату: [протокол вимикачів Tuya](https://developer.tuya.com/en/docs/iot-device-dev/tuyaos_zigbee_switch_demo_product_development_kit?id=Kdva1hnz8cme5).

## Контракт пристрою

| Параметр | Значення |
| --- | --- |
| Виробник / модель | `B-T HOME` / `TS0001` |
| Endpoint | `1` |
| Профіль | Home Automation `0x0104` |
| Тип пристрою | On/Off Output `0x0002` |
| Серверні кластери | Basic, Identify, Groups, Scenes, On/Off |
| Керування | стандартні Off, On, Toggle через On/Off `0x0006` |
| Атрибут стану | OnOff `0x0000`, Boolean |
| Канали пошуку | 11–26 |

Zigbee та HTTP надсилають команди одному `RelayService`: лише його worker
змінює GPIO3 і записує стан у NVS. Zigbee callback ставить команду в обмежену
чергу без очікування; заповнена черга чи несправне реле означає відмову.
Підтвердження ZCL означає прийняття команди, не перевірку механічних контактів
або завершення запису NVS. Веб показує результат виконання та збереження.
Zigbee-атрибут звіряється зі станом виходу кожні 100 мс після обробки черги,
зокрема після зміни з вебу. Підтримуються читання атрибута та стандартне
налаштування reporting/binding шлюзом. Напруги й час живлення залишаються у
вебі та OLED; у цій версії Zigbee передає лише керування/стан реле.

## Налаштування й пам’ять

- `CONFIG_BTH_ZIGBEE_ENABLED=y` — увімкнення адаптера; потрібні ESP32-C6,
  налаштоване реле, підтверджений BOOT GPIO та `BTH_WEB_RELAY_ENABLED` для режиму налаштування.
- `CONFIG_ZB_ENABLED=y`, `CONFIG_ZB_ZED=y`, `CONFIG_ZB_RADIO_NATIVE=y`.
- `CONFIG_ESP_COEX_SW_COEXIST_ENABLE=y` — спільна робота Wi-Fi та IEEE 802.15.4.
- SDK зафіксовано як `espressif/esp-zigbee-lib 2.0.4` у `main/idf_component.yml`.
  Component Manager завантажує його для ESP32-C6 у `managed_components/`.
- `boards/esp32c6_rgb8/partitions.csv`: звичайний NVS залишається на `0x9000`,
  застосунок на `0x10000` збільшено до 2 МБ, `zb_storage` — окремий NVS на
  `0x210000`, 64 КБ. Профіль використовує підтверджені 4 МБ flash.
- Наявні `build/<profile>/sdkconfig` потрібно також оновити: defaults їх не
  перезаписують. Оновлено конфігурації звичайної збірки й VS Code цього workspace.

Автоматичного стирання NVS при помилці немає. Дані Zigbee не ділять розділ із
налаштуваннями доступу та станом реле. Generic-профілі мають Zigbee вимкненим.

Перед запуском SDK адаптер окремо ініціалізує `zb_storage` через
`nvs_flash_init_partition` і перевіряє відкриття простору імен `zigbee`.
Ініціалізації стандартного NVS для цього недостатньо: без цього кроку SDK
2.0.4 викликає `abort()` у `ezb_plat_datasets_init`. Помилка сховища тепер
повертається у Runtime для штатного згортання модулів без стирання даних.

## Перевірка

Host-тести перевіряють жести BOOT, придушення натискання при старті,
взаємне виключення радіомодулів, порядок зупинки й очищення після помилок
ініціалізації/запуску. Також перевіряють обмежений час сполучення, повтори, відсутність накладання
сканувань, успіх/скасування та роботу справжнього `RelayService` із тестовими
чергами й потоками: переповнення, асинхронні команди, HTTP-відповіді, зупинку,
відмову створення worker та повторний запуск. Браузерний тест перевіряє керування
сполученням, підтвердження скидання, вимкнену функцію й втрату зв’язку.
Окремий host-тест виконує код адаптера сховища з підставними NVS-функціями:
перевіряє порядок ініціалізації, помилки відкриття й виділення пам’яті,
звільнення ресурсів та повторний запуск.
Ці перевірки не замінюють перевірку радіозв’язку, живлення, запасу пам’яті й
розпізнавання на реальному шлюзі MOES.

Додаткова збірка `generic_esp32c3` наразі зупиняється на наявному
`static_assert(std::atomic<bool>::is_always_lock_free)` у `esp_mains.cpp`;
це обмеження ADC-адаптера, а не перевірка Zigbee на ESP32-C3.

Основа інтеграції: [ESP Zigbee SDK 2.0.4](https://components.espressif.com/components/espressif/esp-zigbee-lib/versions/2.0.4/readme),
[API запуску й зупинки](https://docs.espressif.com/projects/esp-zigbee-sdk/en/latest/esp32/api-reference/esp_zigbee_sdk.html).
